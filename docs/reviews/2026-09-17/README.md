# 核心 src 审查（2026-09-17）

审查基线：`17af2f8`，分支 `feature/pack-rom-zero-calibration`。
该提交已保存网页诊断、电机/关节单轴调试和此前暂存的 README 修改。

后续已基于 vcan 实施修复，见 [修复及验证记录](fixes.md)。本文和同目录复现脚本保留为原版本的审查快照，下面的“尚未修复”描述仅针对上述基线。

结论：确认 **3 项 P1、1 项 P2**。当前版本可以继续用于网页状态查看，尚不能据此判定实机运动测试已具备完整保护。下面列出的缺陷在本次审查中没有修改；应先修复停止、反馈限位和速度编码问题，再进行现场运动测试。J2 实机方向与反馈对应关系仍待现场验证。

本次阅读覆盖 CAN 协议与驱动、Real/Mock Backend、ros2_control 插件、调试节点、绳索正逆运动学及配置/标定加载、manager 动作和停止流程、WebSocket 网关，以及 URDF、MoveIt、bringup 和输出轴可视化映射。验证使用现有测试、直接调用生产 RealBackend 的虚拟 CAN 探针和网关模拟客户端。没有向实机 `can0` 发送测试运动指令，也没有修改实机标定、方向或限位。

## 1. P1：普通控制停止路径没有撤销电机已接收的位置目标

位置：`src/pi_arm_hardware/src/backend.cpp:465–477`，`src/pi_arm_manager/src/manager_node.cpp:1284–1330`。

manager 的停止/取消先调用 `set_motion_armed(false)`。RealBackend 只关闭写入门禁、切换 MONITORING 并丢弃尚未发送的 A4 队列，没有发送 `0x81`。manager 随后发出的保持轨迹也会被已经关闭的写入门禁挡住。

虚拟 CAN 抓帧确认：发送位置目标后，撤销授权并尝试保持写入，A4 数量不再增加，`0x80/0x81` 数量均为零。驱动器已经接收的目标没有被这条路径撤销，因此在电机尚未到达最后目标时，不能保证点击停止就停止运动。这是代码与协议层面的结论，不是实机停止距离测量。

影响范围是普通 `DirectMove` / ros2_control 链路；新 commissioning 路径已经单独调用 `stop_motors()`，不属于这个缺陷。单纯“停止继续发帧”也不能替代驱动器停止确认。

建议：区分“撤销写入授权”和“停止已发送运动”，在停止、取消、故障退出时执行有结果确认的驱动器停止；失败须保留未确认状态并阻止再次授权。注意与控制线程、管理操作的并发顺序，避免停机等待阻塞实时控制循环。

## 2. P1：反馈只检查输出轴包络，没有检查恢复后的关节限位

位置：`src/pi_arm_hardware/src/backend.cpp:360–375, 440–442`，`src/pi_arm_hardware/src/axis_test.cpp:168–170`。

逆解成功即设置 `kinematics_valid=true`，之后允许控制；没有逐关节对照 `joint_lower_limits_rad` / `joint_upper_limits_rad`。输出轴包络是所有关节姿态的外包范围，不能替代耦合后的关节限位。

复现：使用有效的虚拟零偏标定，注入对应 `joint_05≈35°` 的反馈，其 URDF 上限为 `30°`。生产 Backend 返回：

```text
q5_deg=35.0004 kin=1 control=1 error=NONE
```

普通 DirectMove 的起点验证仍可能拒绝后续请求，但它不能修正错误的反馈许可，也不能保护已经运行的 commissioning 关节测试。后者只检查 `sample.kinematics_valid`，会漏掉仍在输出包络内的关节越界。

建议：反馈逆解后增加逐关节限位状态，保留原始角度及解算角度供诊断，发布关节名称、实际值和边界；正常控制/关节测试禁止继续，并触发可确认停止。原始电机方向调试应保留明确的独立许可，不能再把它与模型正常状态混为一谈。

## 3. P1：整数速度编码改变速度上限，并使关节测试偏离预检路径

位置：`src/pi_arm_hardware/src/axis_test.cpp:80–94, 101–119`，`src/pi_arm_can/src/protocol.cpp:35–40`。

预检假定所有输出轴按同一进度线性插值；实际发送的是各自独立的 A4 目标和速度。速度先提升到至少 1 协议度/秒，再由 `llround` 取整。低速时不同电机的归一化进度因此不同，实际允许的运动路径与预检路径不一致。

两个复现：

- CAN4 请求输出轴 `+0.1°`、`0.05°/s`，实际帧为目标 `0.6` 协议度、速度 `1` 协议度/秒。按配置比值 6 换算，编码速度上限为 `0.1667°/s`，是请求上限的约 3.33 倍。这里测得的是编码上限，不是实机测得速度。
- 从 `joint_05≈29.9902°` 开始，请求 `joint_02 +0.1° @ 0.05°/s`，预检通过。抓取各电机实际 A4 整数速度，按独立匀速运动计算 0.5 秒的中间反馈并注入，得到 `joint_05≈30.0093°`，而 Backend 仍返回 `kin=1 active=1`。这一可行中间状态已越过 30° 限位，且运行时未停止。该模型没有模拟真实加减速；它证明当前预检不能覆盖实际编码允许的轨迹，不代表实机必然复现同样数值。

建议：根据各电机协议分辨率显式处理不可表示的速度，不能静默提高用户上限；路径检查使用编码后的目标与速度。耦合运动须有同步执行或保守的异步路径边界，并结合逐关节在线限位保护。仅增加当前线性路径的采样点数不能解决该问题。

## 4. P2：网关在动作已经接受后，可返回失败却留下动作运行

位置：`src/pi_arm_websocket/pi_arm_websocket/gateway.py:200–221`。

`send_goal()` 收到 accepted 后保存动作句柄，随后等待首次反馈中的 task_id。若这条反馈未在超时内到达，就向网页抛出“manager 未返回任务 ID”，但没有取消已接受动作，也没有向用户返回“已接受、执行状态待确认”。网页请求失败与实际执行状态不一致。

模拟 ROS 客户端使目标接受但不发送首次反馈，实际生产方法返回：

```text
gateway_error= manager 未返回任务 ID
goal_accepted= True cancel_requested= False active_goal_count= 1
```

这是普通动作链路的问题；commissioning 的 AxisTest 服务不经过该函数。建议对已接受动作的超时明确反馈执行状态，或执行取消并确认；同时处理目标接受响应晚到的情况，避免遗留无人跟踪的动作。

## 已验证与仍待现场确认的边界

- 现有 `colcon test` 结果：**132 tests, 0 errors, 0 failures, 0 skipped**。通过这些测试不能否定上述额外复现；现有即时到位的 vcan 模拟器没有覆盖耦合运动的中间过程。
- 绳索模型已有正逆映射、Jacobian 有限差分、非有限输入、反三角函数定义域、奇异点及配置加载测试。本次未发现这些测试所覆盖的公式内部一致性问题。
- 公式正逆自洽不证明实物方向正确。当前 J2→下游输出的耦合符号、各电机 `motor_direction`、减速比、ROM 零位与软件偏置，需要不同姿态的实际数据共同验证。一个装箱姿态的偏置拟合无法独立证明方向正确。
- 历史 R02 标定的 `approved=true` 表示文件记录状态，不等于本次审查重新确认了硬件映射。没有依据推断 J2 差异必然来自某一方向符号，故未修改方向或放宽限位。
- 本次没有测量电机真实加减速、停止距离、负载下的绳索弹性/回差和通信恢复行为。现场恢复供电后，先确认网页六轴新鲜反馈及错误状态，再按修复后的低速流程逐轴采集方向。

## 复现材料

`evidence.txt` 保存审查时的关键输出。`probe_backend.cpp` 直接链接工作区生产库；`reproduce.py` 生成临时虚拟标定、编译探针并回应虚拟 CAN。探针仅绑定 `vcan0`，Python 入口还检查接口类型确实为 vcan；不会创建接口、启停实机服务或使用真实标定进行控制。

这些脚本是针对 `17af2f8` 的缺陷复现快照，断言的含义是“观察到了已知缺陷”，不是安全验收通过。后续修复后相关断言失败是预期结果。C++ 探针的关节边界和映射固定为审查版本的数据。

先构建工作区，并确保已存在且没有其他模拟器/驱动占用的 `vcan0`，然后在仓库根目录执行：

```bash
source install/setup.bash
python3 docs/reviews/2026-09-17/reproduce.py
python3 docs/reviews/2026-09-17/gateway_timeout.py
colcon test --event-handlers console_direct+
colcon test-result --verbose
```

依赖：工作区已构建的库、g++、Python PyYAML、iproute2、ROS 2 环境，以及已配置的虚拟 CAN。
